SentryGate

A security gateway for LLM APIs — and the cache-shaped hole in every one of them.

Presented byDivyansh Sharma
Phase1 of 4 · 18–22 Aug
Repositorygithub.com/divyansharma001/SentriGate
The claim
A semantic cache in front of an LLM is an unscreened path to a screened-out response.

The filter is not weak. On a cache hit, it is simply never asked.

Why this matters

Semantic caching is standard practice.
So is putting it in front of the filter.

~50× Latency saved on a hit — roughly 800 ms of inference becomes ~15 ms of vector lookup.
$0 Token cost on a hit. This is the entire commercial reason semantic caches get deployed.
0 Filter invocations on a hit. Screening runs on the miss path, because running it on hits would erase the win above.

The optimisation and the vulnerability are the same design decision.

The problem

Two lanes. Only one of them is defended.

make demo

  • Every threshold anyone actually deploys leaks 100% of surface mutations.
  • Raising it to 0.95 still leaks 40% — and collapses the cache hit ratio that justified the cache.
  • There is no setting that is both useful and safe. The fix has to be structural, not numeric.
The contribution

Make the filter the retrieval predicate.

Today — similarity only

search(vector) → nearest neighbour → return if sim ≥ 0.85 security state: not consulted

SentryGate — verdict-filtered

search(vector, filter={ is_injection: false, risk_level: ≤ request.risk, intent: == request.intent }) → incompatible verdict = no hit
  • Verdict computed once at screening, stored in the Qdrant payload beside every cached response.
  • Intent-dependent thresholds — tight for credentials, tool-use and PII; relaxed for informational queries.
  • High-risk hits force re-verification, so the classifier runs where it pays for itself and nowhere else.
