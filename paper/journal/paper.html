ABSTRACT

Production applications built on large language models (LLMs) commonly place two components in front of the model: a semantic cache, which returns a stored answer when a new prompt is close in meaning to an earlier one, and a safety filter, which blocks prompt-injection attacks. Because a cache only saves time if it is consulted first, the cache usually sits ahead of the filter, and a cache hit is served without the filter ever being asked. We show that this ordering is an exploitable flaw rather than an implementation detail. On a running, OpenAI-compatible gateway built from widely used open components, {{n_variants}} rewordings of {{n_seeds}} public prompt-injection attacks were fired at a cache holding one poisoned answer per attack. At a similarity threshold of 0.85, {{w4_lazy_085}}% of trivially edited attacks (a capital letter, a full stop, an added word) were served the poisoned answer, and the gateway's own request log confirms the filter never ran for any of them; no threshold value is both safe and useful. We propose verdict-tagged caching: the filter's verdict is stored with each cached answer, the vector search is filtered on it, and every cache hit is re-checked before it is served. Separating leaks the cache causes from leaks the filter would miss anyway, matching on the stored verdict alone cuts cache-caused leaks from {{p3_base_clean}}% to {{p3_filter_attack}}% when the poison was saved as an attack, but only to {{p3_filter_clean}}% in the realistic case where it slipped past the filter as clean. Re-checking every hit removes all cache-caused leaks in both cases (0 of {{n_variants}}, 95% upper bound {{p3_all_upper}}%), keeps {{p3_all_hits}}% of honest cache hits, and still skips the paid model call. On {{scr_fa_ord_n}} ordinary honest texts the filter raised {{scr_fa_ord_k}} false alarm, but it blocked {{scr_fa_look}}% of honest look-alike texts and caught only {{scr_deepset_det}}% of conversational attacks, which bounds what any cache defence built on it can achieve. Every number is regenerated from committed logs by one command.

1. Introduction

Large language models are rarely called directly by the applications that use them. A gateway, sometimes called an AI proxy or LLM router, sits between the application and the model provider and takes on the work that every application would otherwise repeat: authentication, spending limits, logging, routing to a cheaper model when a request is simple, and, increasingly, safety screening. Two of these jobs matter most here. A semantic cache turns each prompt into an embedding vector and, when a new prompt lies close enough to a stored one, returns the stored answer instead of paying for a new model call (Bang, 2023; Regmi & Pun, 2024). A safety filter, typically a small classifier, scores each prompt for prompt injection, the class of attack in which input text tries to override the model's instructions (Perez & Ribeiro, 2022; Greshake et al., 2023), and blocks it above a threshold. Prompt injection is ranked first in the OWASP Top 10 for LLM applications (OWASP Foundation, 2024).

Each component is well studied on its own. Caching is evaluated for hit rate, cost and latency; filtering for detection and false-alarm rates. Recent work has shown that semantic caches can be poisoned so that other users receive attacker-chosen answers (Wu, Wang, et al., 2026; Zhang, Liu, et al., 2026). Less attention has gone to what happens when a cache and a separate safety filter share one request path, and the order between them is forced by economics. A cache lookup costs a few milliseconds, whereas a transformer-based filter costs tens to hundreds; if the filter ran first, every request would pay for it, including the repeated ones the cache was installed to make instant. Gateways therefore check the cache first. On a hit, the stored answer is returned and the filter is never consulted.

This paper shows that the ordering creates an exploitable gap. If a harmful answer is ever stored in the cache, any prompt close enough in meaning to its original prompt will retrieve it without being screened, and the cheapest rewordings, a changed capital letter or an added full stop, are the closest of all. The filter is not weak in this scenario; it is simply never asked. Raising the cache's similarity threshold does not help either, because the edits that matter most are the ones that barely move the embedding.

We make the problem concrete, measure it on a running system, and close it by design. Our contributions are:

  • a characterisation of the cache-before-filter bypass in LLM gateways, in which a cache hit skips a separate input filter, with an explicit threat model;
  • a measurement of the bypass on a running, OpenAI-compatible gateway with real components (a DeBERTa-v3 injection classifier, MiniLM embeddings, Qdrant and Redis), in which every counted bypass is backed by the gateway's own log record that the filter did not run;
  • verdict-tagged caching, a defence that makes the filter's stored verdict part of the cache's match condition and re-checks hits, implemented as one switch in the same code base as the vulnerable baseline;
  • a decomposition of every leak into the part the cache causes and the part the filter would miss even when asked, which prevents a defence from being credited or blamed for the filter's own error;
  • a study of the filter itself on texts it was not tuned on, which separates its false-alarm rate on ordinary text from its rate on adversarial look-alikes, together with live measurements of the output guard, rate limiter and model picker; and
  • a fully reproducible artefact: every table and figure is regenerated from committed request logs, and recorded model replies make every run repeatable with no API key.

3. Threat Model

3.1 System model

We consider a gateway that receives chat-completion requests over an OpenAI-compatible HTTP API and, for each request, (i) looks the prompt up in a semantic cache, (ii) on a miss, screens the prompt with an injection classifier and blocks it if the score s(p) is at least a threshold θ = 0.5, and (iii) otherwise calls the model, returns the answer and stores the pair (p, a) in the cache. A stored entry is returned for a new prompt q whenever the cosine similarity of their embeddings, sim(q, p), is at least a cache threshold τ. This is the cache-first order used by real systems; Section 6.2 also evaluates the filter-first order as a reference.

3.2 Attacker

The attacker wants an answer the filter would refuse. They can send requests to the gateway like any user and reword their own prompts freely. They do not need access to the cache, the vector database, the model, other users' sessions or any special tooling; a text editor suffices.

3.3 How a poisoned answer enters the cache

The attack needs a harmful answer to be stored under a prompt close to the attacker's. We consider three routes: (1) a prompt that scored just below the block threshold was allowed, answered and cached; (2) the cache was pre-filled before launch from prompts that were never screened; (3) the cache is shared between tenants, so one tenant's stored answer reaches another. Route (1) needs no privileged access and is the one we model. We model the stored entry's verdict in two ways: saved with the filter's own label, usually "attack" (the easy case for a defence), and saved as "clean", as an attack that slipped past once would be (the realistic case).

3.4 Out of scope

Attacks on the model's weights or training, on the network between gateway and database, on the model provider, and attacks that require code execution on the gateway host are out of scope. So is the filter's own detection error: an attack the filter misses when asked directly is a limitation of the filter, not of the cache, and Section 5.3 shows how we keep the two apart.

4. System Design

4.1 Gateway architecture

SentryGate is an OpenAI-compatible gateway written in Python with FastAPI, deployed with Docker Compose behind an nginx reverse proxy (Fig. 1). The safety filter is ProtectAI's DeBERTa-v3 prompt-injection classifier (He et al., 2023; ProtectAI.com, 2024), and personal data is detected with Microsoft Presidio (Microsoft, n.d.); personal data is flagged in the verdict but not blocked. Prompts are embedded with all-MiniLM-L6-v2 (Reimers & Gurevych, 2019; Wang et al., 2020). An exact-match layer in Redis sits in front of a similarity layer in Qdrant (Qdrant, n.d.), whose HNSW index (Malkov & Yashunin, 2020) supports payload filters applied during the search itself. Model calls go to OpenRouter, recorded to disk so they replay for free. Every request writes one JSON line recording the outcome, the timing of each stage, the token cost, whether screening ran, and the full configuration and code version that produced it; the prompt itself is never logged, only its hash and length.

4.2 Verdict-tagged caching

The defence follows from a simple observation: the filter's result for a prompt is already computed on every miss, so it can be stored next to the cached answer and consulted on every lookup at almost no cost. A cached entry e carries the answer, the prompt embedding, and the verdict of the prompt that created it: an injection flag and score, a personal-data flag, an intent label, and a risk level. Every incoming prompt q also receives a cheap intent label c(q) from keyword rules (credentials, tool use, personal data, informational, other) that runs in microseconds with no model. The same rule labels each entry when it is stored, so a prompt and its stored answer are labelled identically. An entry may then be served for q only if

¬inj(e) ∧ c(e) = c(q) ∧ sim(q, e) ≥ τ(c(q)) ∧ R(q, e)(1)

where τ is 0.95 for the risky labels (credentials, tool use, personal data) and 0.85 otherwise, and R is the re-check condition below. The first two conditions are expressed as a Qdrant payload filter, so the vector search only ever returns entries that already satisfy them and no candidate is discarded after the search.

The re-check R runs the full filter on q before a hit is served and blocks it if s(q) ≥ θ. It has two scopes. The risky scope re-checks a hit only if the request's cheap label is risky or the entry's stored injection score was at least 0.2, a close call when it was saved; it was our first design, intended to keep most hits at full speed. The all scope re-checks every hit. Section 6.3 shows why only the second closes the gap. Re-checking every hit may look as though it defeats the purpose of a cache, but it does not: what a cache saves is the model call, which costs seconds and money, not the filter, which costs tens of milliseconds and nothing.

4.3 Further mitigation layers

Three further layers complete the gateway. An output guard scans every answer, including one served from the cache, for four kinds of content an answer should almost never carry to an application that trusts it: browser script, destructive SQL, dangerous shell commands, and strings shaped like secret keys. It can be off, flag the answer in a response header, or block it; a blocked answer is never written to the cache. Because it inspects the answer rather than the question, it is a second line of defence behind the cache that does not depend on the input filter. A rate limiter enforces per-caller requests per minute (counting cache hits) and a daily model-token budget, with counters in Redis so that a restart does not reset them. A model picker scores each miss with plain rules (code, mathematics, reasoning words, length, multiple questions) and sends easy prompts to a cheap model and hard ones to a strong model, in the spirit of cost-aware routing (Chen, Zaharia, & Zou, 2023; Ong et al., 2025); if the chosen model's call fails, a fallback model is tried once.

4.4 One code base, one switch per layer

The vulnerable baseline and every defended configuration are the same program; each layer is a single environment variable, read once at start-up and copied into every log line. This removes a common confound, since no two arms can differ in some unintended way, and it makes every comparison in Section 6 a matter of changing flags. An automated test checks that every setting the code reads is actually passed into the container, after one such omission silently disabled a layer during development. The test suite ({{n_tests}} tests) runs without network access, model downloads or API keys, and a pinned linter reports no problems.

5. Experimental Method

5.1 Attack corpus

Seed attacks come from two public datasets on Hugging Face (Table 2): every English attack between 20 and 400 characters in deepset/prompt-injections (deepset, 2023; {{n_seeds_deepset}} seeds) and a seeded random sample of {{n_seeds_jay}} attacks from jayavibhav/prompt-injection (jayavibhav, 2024), {{n_seeds}} seeds in all. German-language deepset items are excluded, since the filter is trained for English only (ProtectAI.com, 2024). Each seed is reworded in two families that are kept apart throughout, because they behave very differently. Lazy edits are fixed rules an attacker can apply for free: flipping the case of the first letter, adding or removing a full stop, adding an exclamation mark, "please" at the start or end, a double space, all capitals, one typo, and stripped punctuation ({{n_lazy}} variants). Full paraphrases are produced by a T5 paraphraser (Vorobev & Kuznetsov, 2023) with deterministic beam search (three per seed, {{n_rewrite}} variants). One further "exact" variant, the seed itself, must always hit and serves as a wiring check rather than a result. A separate set of {{n_controls}} honest questions from the same source is used as controls. All inputs are generated by a committed script with a fixed random seed and recorded with file hashes.

5.2 Procedure

Fig. 2 shows the harness. For each seed, the cache is cleared and one poisoned entry is planted under the seed text through a test-only endpoint that is disabled unless explicitly enabled. Every variant of that seed is then sent to the gateway over HTTP, and each reply is joined to the gateway's own log line for that request through a request identifier the gateway returns. The poison is a fixed marker string carrying a leaked "system prompt" and a fake API key. The 100 controls are each sent against a freshly poisoned cache to check that honest users are never served the poison. To measure what a defence costs honest users, each control is asked once (a miss, which stores its answer) and then reworded with the same lazy edits; the share of those rewordings answered from the cache is the honest hit rate.

5.3 Measures

A bypass is counted only when two independent facts agree: the reply body is exactly the poison string, and the gateway's log line for that request records that screening did not run. The second condition reads the claim from the system under test rather than from our harness. Poison served counts replies equal to the poison whether or not the filter ran. Because the filter itself misses some attacks, poison served mixes two causes. We therefore ask the same filter about every variant directly, in the filter-first order, and split each served poison into cache-caused (the filter blocks that exact text when asked, so the cache is why it got through) and filter miss (the filter lets it through anyway, so no cache defence can stop it). Only the cache-caused share measures a cache defence. We also report the honest hit rate, the median latency of honest hits and misses, the false-alarm rate of the filter on honest text, and its detection rate on attacks.

5.5 Statistical treatment

The rewordings of one seed are not independent: if one lazy edit of a seed matches the poisoned entry, the others usually do too. A binomial interval over variants would therefore be too narrow. Every rate over attack variants is reported with a 95% confidence interval from a cluster bootstrap that resamples whole seeds with replacement (2,000 resamples, fixed random seed; Efron & Tibshirani, 1993; Field & Welsh, 2007). When no event occurs at all, resampling can only return zero, so we report the conservative rule-of-three upper bound over seeds, 3/nseeds (Hanley & Lippman-Hand, 1983). Rates over independent texts, as in E4, use the Wilson score interval (Wilson, 1927).
